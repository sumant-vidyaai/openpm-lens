# Decisions and roadmap

Decisions agreed with the project owner on 15 October 2026.

## Decisions

| Topic | Decision |
|---|---|
| Licence | Apache-2.0 (explicit patent grant, clear contributor terms). |
| Hosting | Cloudflare Pages free plan (static files; no project data ever reaches the host). Indian mirror optional later. |
| Blocked browsers | Tools that block direct browser calls (e.g. Jira Cloud) are file-import only in v1. No hosted proxy, because it would break "no data to any server". |
| Live API connectors | Only where the tool allows browser calls (e.g. Azure DevOps). Optional and clearly marked; tokens in memory only. |
| Metric grouping | Two neutral tags per card: `domain` (broad group) and `area` (traditional group). No third-party framework names or trademarks. |
| Sample data | Synthetic only, imitating each tool's export format. From the owner's PPM exports, column headers only, never rows. |
| Missing planned hours | Default "exclude and flag". Optional "treat as zero" with the assumption flagged. Missing actual hours or percent complete always exclude. |
| Percent complete | Visible per-tool setting (tool-reported, 0/100, 50/50, status-based). |
| Stack | TypeScript, Vite, React, Vitest; static site on Cloudflare Pages; offline support via service worker; GitHub Actions for tests. |
| Privacy rules | No tracking or analytics; nothing loaded from other websites at runtime; strict browser security policy; downloadable release bundle with checksum; dependency list kept small. |

## Connector order (proposed)

1. Generic CSV/XLSX importer with column mapping.
2. MS Project XML (MSPDI).
3. Jira CSV.
4. Azure DevOps (CSV, then browser REST).
5. Flow-focused tools (Linear, GitHub Projects, Trello, ClickUp).
6. Enterprise PPM (Clarity, Workfront, ServiceNow, Planview, Smartsheet).

## v0.12 – More metrics (Batch 3)
**Forecast (Import tab):** EAC, ETC, VAC and TCPI. The user chooses how the rest of the work is expected to go (three EAC methods: BAC/CPI; AC + BAC - EV; AC + (BAC - EV)/(CPI x SPI)); the choice is shown. BAC = planned hours of the tasks used, not necessarily the whole project (stated on screen). TCPI is withheld with a reason when spend already equals or exceeds the budget (or forecast). The CPI x SPI method needs a status date. Included in the summary CSV.
**Earned schedule (Import tab):** ES = C + (EV - PV_C)/(PV_C+1 - PV_C); SV(t) = ES - AT; SPI(t) = ES/AT. Formulas checked against Walt Lipke's introduction at earnedschedule.com (the source gives no rule for after the planned end). Our rules, stated on screen: AT counts counted days (weekdays or calendar days) from the first planned start to the status date, both included, and keeps counting after the planned end; if all planned work is earned, ES is capped at the planned duration. The curve uses only tasks usable for schedule measures; a test checks the curve matches PV at the status date. Verified against an independent Python calculation (ES 8.7143, AT 13, SPI(t) 0.6703 for the Website redesign sample).
**Flow metrics (new tab):** WIP, throughput, cycle time, work item age. Definitions follow the Kanban Guide (prokanban.org): WIP = started not finished; throughput = finished per unit time; cycle time = started to finished; age = started to now. The guide does not say how to count days or which percentile method, so our rules (on screen): calendar days counted inclusively (same day = 1); nearest-rank percentiles, shown only with at least 5 finished items else "Insufficient data"; window = last N blocks of 7 days ending on the status date (not calendar weeks). Status date is required, never assumed. "Created" is never guessed as a start date (it would be lead time; warned if chosen). Left out and listed: cancelled, unclear dates, marked done without a done date, done before start, no dates, starts after status date. Finished items without a start count in throughput only. Every item is accounted for exactly once (test).
- Tests: 190 pass. Open: flow metrics need real header lines from Jira/Azure DevOps/etc. to suggest start/done columns; Jira's standard CSV has no "work started" date (needs changelog), so users must supply one.

## v0.13 – Batch 3b part 1: Schedule, Cost in money, Resources (inserted before Batch 4, agreed with the user)
**Why:** the app covered cost and schedule in hours and flow, but not resource, quality or cost in money. Plan agreed: Batch 3b before Batch 4, in two deliveries (v0.13: schedule extras, money, resources; v0.14: quality, charts, MS Project XML).
**Architecture:** the Import tab now publishes its worked-out data (table, items, hours tasks, schedule tasks, status date, date order, day count) to the other tabs (`SharedData`); rows line up one-to-one. New tabs reuse the Import tab's column and unit choices and add only their own picks. All tabs stay mounted (hidden) so loaded files and settings survive tab changes (previously the Import tab lost its file when you left it).
**Schedule tab:** variance = actual finish - planned finish in calendar days (positive late); on time = on or before planned finish; overdue = open task whose planned finish is before the status date. On-time % and median need at least 5 finished tasks (else "Insufficient data"). Left out and listed: cancelled, unclear dates, no planned finish, marked done without a finish date. Every task is counted exactly once (test).
**Cost in money tab:** hours x hourly rates entered by the user (default rate and/or per person); one currency, label only, no conversion or lookup; invalid rates ignored; a task without any applicable rate is left out and listed (never a guessed rate). Same task rules as hours. A task naming several people (";" separated; commas are read as part of one name) uses the default rate only if none of them has an own rate, else it is left out. Money CPI can differ from hours CPI (stated). Forecast in money offers the two methods that need no planned value.
**Resources tab:** planned hours spread evenly over planned weekdays (or calendar days, from the Import setting), summed per person per week (weeks start Monday); utilisation = load / weekly capacity (default 40 h, editable, own capacity per person); weeks above a user-set limit (default 100%) are flagged with a symbol. Tasks naming several people are left out (split unknown); unassigned work has its own row. Planned vs actual per person uses tasks that have both. Capped at 104 weeks shown. Rules are this app's own arithmetic, not a standard.
**Verified:** all three checked against independent Python calculations on a made-up team file (60% on time, EV 6,240, AC 6,530, BAC 9,300, weekly utilisation per person). 207 tests pass.
**Open / known limits:** CSV exports from MS Project may include summary (parent) rows whose hours repeat their children's, which would double count; to be handled with the MS Project XML importer (which flags summary tasks) in v0.14. Assignee, type and severity columns are not yet in the Tool coverage matrix.

## v0.14 – Batch 3b part 2: Quality, charts, MS Project XML

## v0.18 – Fill-in template (roadmap batch A)
**Why:** the user's idea: define our own template that people fill in and upload to get the numbers. It also removes the need to name which project tool someone uses.
**What was built:** a downloadable **Excel workbook** (sheets: Start here, Tasks, Settings, Rates) and a **plain CSV** with the same 18 column headings (Project, Programme, Team, ID, Task, Type, Status, Assignee, Planned start, Planned finish, Actual start, Actual finish, Estimate (h), Actual (h), % complete, Created, Severity, Found in), plus a **filled made-up example** of each (two projects, 14 tasks). **Rules of the template (shown to the user):** effort in hours, percent 0 to 100 (write 40, not 40%, because Excel stores 40% as 0.4), dates as year-month-day typed as text so Excel cannot reinterpret them (real date cells are also read), a blank is "not known" and never 0. ## v0.19 – Batch 1: Explain and accuracy
**Why:** after v0.18 the numbers were there but not the "why" or the timing. Agreed roadmap Batch 1 (docs/roadmap.md).
**What was built:**
1. **Holidays and leave.** Template sheets **Holidays** and **Leave** (and a holiday box on Portfolio). Holidays apply only when days are counted as weekdays; they are skipped in planned value, earned schedule and the planned-value curve. Leave: each Monday-to-Friday day a person is away (or a holiday) takes one fifth off that person's weekly capacity. A week with no capacity but planned work counts as over the limit (utilisation shown as "no capacity"). Resources shows "(capacity N h)".

## v0.22 – Finish-date forecast and status report (Batch 4)
**Method (checked against two independent published sources, ProKanban forecasting pocket guide and a Xebia article on forecasting without estimation):** Monte Carlo on weekly throughput. Each trial draws a past weekly count at random (with replacement), subtracts it from the open items until none remain and records the weeks; 10,000 trials; read at 50% (coin flip, never commit), 85% (usual commitment), 95% (costly deadlines). Items are counted, not points. Starting rules, not standards: default history 12 weeks (editable), no forecast under 4 full weeks, warning under 6 and over 26.
**Choices:** fixed random seed (1) so the same file always gives the same answer; week 1 is the 7 days ending on the status date; a week's work counts as done at its end (dates err late); the window never reaches before the first actual start (or first finish), so weeks before the work began are not counted as quiet; quiet weeks inside the window stay as 0; all-zero history gives no forecast rather than an invented pace; milestones are left out of the counts; "extra items" lets the user add scope.
**Milestone forecast:** without task dependencies the work a milestone needs is not known. The open items planned to finish on or before its planned date are used and the assumption is printed on screen. Items without a planned finish are listed as left out, not guessed.
**Status report:** sentences are written by a tested function from the numbers (health, CPI/SPI, counts, defects, milestones, forecast, RAID). They state what the numbers show, never why; missing facts are omitted. The person adds highlights, concerns, decisions and next steps in boxes (not saved). Printed through the browser print window as before; one A4 page for the example.
**Bug found and fixed:** the page shell's minimum height made every print end with a blank extra page; removed in print.
**Verified:** 20 new tests (314 -> 334); exact probability calculation (dynamic programming, independent of the simulation) gave 4/6/7 weeks for the example against the app's 4/6/7, and 31% against the app's 32% (sampling error); milestone 85% date matched; axe clean and no overflow at 360 px in light and dark.
**Limits:** equal-size items assumed; the drags on cost and schedule are not yet in the report sentences; trend since the previous snapshot is not in the report yet; the forecast is for counts of items, not hours.

## v1.1 – Planning (Batch 6)
**Formulas confirmed from independent sources before coding** (pressbooks pm4id "Critical Path and Float"; pmstudycircle PERT calculator, float and reserve pages): expected = (O + 4M + P) / 6; SD = (P - O) / 6; total SD = square root of the sum of squared task SDs (independence assumed and stated); forward pass ES = max EF of predecessors; backward pass LF = min LS of successors; total float = LS - ES; free float = ES(next) - EF; critical = total float 0; cost baseline = estimate + contingency; project budget = baseline + management reserve.
**Convention:** a task with start offset s and d counted days occupies days s to s+d-1 and finishes at offset s+d (0-based, end-exclusive), so free float needs no -1. A milestone has length 0 and shows one date (when its last predecessor finishes).
**Template (columns and settings only appended):** Tasks: Optimistic (h), Pessimistic (h), Depends on. Settings: Contingency reserve (h), Management reserve (h), after Risk high from, so the existing list references still point at the right cells. Reserves accept 0; blank means not entered; neither is ever defaulted or suggested.
**Dependencies:** a Depends on cell lists task IDs separated by commas or semicolons. Anything written with a lag, lead or link type is reported and not used. Microsoft Project XML links are read only when Type is 1 (finish-to-start, confirmed in the schema reference: 0 FF, 1 FS, 2 SF, 3 SS) and the lag is 0; other links, lagged links and links to summary or unnamed tasks are counted in the notes.
**Network faults:** unknown predecessor, self-dependency, duplicate ID, bad length and cycles are reported as problems; a cycle stops the calculation rather than returning a guess. Tasks without both planned dates are left out and listed, and links to them are dropped with a warning that the path may look shorter than it is.
**Views:** whole plan (all tasks, planned dates, from the earliest planned start) or remaining work (finished tasks take no time, dates counted from the status date; a started task keeps its full planned length, stated on screen).
**Reserves:** the check compares the typical overrun (estimate / CPI minus the estimate) with the contingency reserve, then the management reserve, and says who controls each layer. It is a rule of thumb and is labelled as such.
**Baseline lock:** the baseline snapshot cannot be deleted, replaced by saving the same status date, or taken over by an imported snapshot. Moving it needs a written reason (10 to 300 characters) saved with the new baseline together with the date of the one it replaced. Optional fields only, so the snapshot format stays version 1 and older files still load. "Delete all snapshots" remains, behind its own confirmation.
**Limits:** finish-to-start only, no lags; Planning works on one network at a time (pick a project if IDs repeat); three-point range assumes independent tasks.

## v1.4.1 – Portfolio part 2 (priority score, demand against capacity, risks across projects)
**Template (appended only):** a new optional "Priority" sheet (same layout as Scoring: criteria across row 1, weights in row 2, one project per row) and an optional "Project" column at the end of the Risks sheet. The template now has 19 sheets. Old files still work; a Risks sheet without the column raises no complaint.
**Priority score:** the PMO's own criteria, weights and 1-to-any-scale scores, typed on the Portfolio screen or loaded from the Priority sheet. Score = sum(weight x score) / sum(weights), the same rule as vendor and option scoring (one formula, no second version). A project missing any weighted score is **unscored, never zero**; ties share a rank; criteria without a positive weight are left out and listed. Projects with no scores are listed. Weights and scales are never suggested. The ranking informs a funding decision; it does not make it.
**Demand against capacity:** every loaded project's tasks (assignee column found the same way as on the Resources tab) are combined and run through the existing resource arithmetic: planned hours spread evenly over each task's counted days, load per person per Monday-week, utilisation = load / capacity. Weekly hours per person is **entered by the user** (or taken from the template's "Weekly capacity (h)") and is never defaulted; the 100% flag is the arithmetic meaning of "over capacity". The "everyone together" row adds planned hours and capacity first and then divides (ratios are never averaged); unassigned work is reported separately and not counted. A person is called out as "over only when projects are added together" when they exceed the limit overall but no single project puts them over. Tasks naming several people, with no planned hours, or with no dates are left out as on the Resources tab. Personal capacity and leave remain on the Resources tab (one project).
**Risks across projects:** one probability-by-impact heat map of all OPEN risks, counts of high / medium / low / not scored / overdue actions per project (worst first) and the top ten open risks naming their project. A risk goes to the project in its Project column; with no column it goes to the file's only project, else it shows as "(no project named)". Risk limits come from the template Settings or the starting values 7 and 13 (not a standard).
**Learn:** three new terms and three "which question does what" rows.

## v1.5.0 – Finishing earlier batches (weights check, go / no-go checklist, load an archive, RFQ)
**Template (appended only):** a new optional "Gate checklist" sheet (Criterion, Owner, Met, Note). The template now has 20 sheets. The RFI-RFP Type list gains RFQ. The example go / no-go row is filled in so the new cross-check can be seen.
**Weights check (sensitivity):** for the leading option and each criterion, the weight at which another option would draw level, moving that one weight with the others unchanged. Exact, not simulated: two options tie where S_a + w x a = S_b + w x b, so w = (S_b - S_a) / (a - b); the divisor "sum of weights" is the same for both and cancels. Only weights from 0 upward count (0 means dropping the criterion). Reported as the new weight and the change in percent of the current weight, lower and higher. If the leader beats or ties every rival on each criterion separating them, it "holds for any weight". A tie at the top, or fewer than two fully scored options, gives no leader to test and says so. No threshold such as "robust if 10%" is built in: whether a move of that size is plausible is the user's judgement. Shown on Choose and justify and under the Portfolio priority score. Checked by hand: weights 2 and 1, A (8, 4) against B (5, 9), tie at Price 5/3 and Fit 1.2; example workbook Price 80, Fit to needs 16.67.
**Go / no-go checklist:** the user's own criteria (the app supplies none, and weighs none above another), each Yes, No, Not applicable or blank (not answered). Counts are shown. The app only lines the list up with the recorded decision and states mismatches: a Go with criteria marked No or unanswered; a No go or Hold when every applicable criterion is Yes. It never recommends a decision.
**RFQ:** Type in the RFI-RFP sheet accepts RFQ (request for quotation: a price on something already specified), alongside RFI (information) and RFP (proposal). The tracker shows counts by type (capitals ignored, blank listed as "(no type)"). Any other word the user types is counted under that word.
**Load an archive back:** choose the zip made by "Download archive" on the Import tab. Only a zip whose README.txt starts "Spashta archive" is accepted; anything else is refused with an explanation. The zip reader accepts stored files (as Spashta writes them) and deflate-compressed files (as other tools write them, using the browser's own decompression); password-protected or other methods are refused. Tasks come back as the Tasks sheet when they are in the template layout, otherwise as a generic table with the column-mapping step shown; each archived sheet comes back under its template name; the status date is read from the README. Figures are worked out again, nothing is stored in the archive as a result. **Not part of an archive:** Settings other than the status date, Rates, Holidays, Leave, the Portfolio Projects and Priority sheets, and snapshots (snapshots.json sits inside the zip; unzip it and add it on the Trends tab).
**Learn:** four new terms and three new "which question does what" rows.
**Checked:** 477 tests pass (new: sensitivity by hand, checklist counts and consistency rules, RFQ counts, zip reading including a deflate-compressed zip, archive round trip of risks, scoring, go record, RFI-RFP and gate checklist); example workbook, made-up portfolio and an archive made from the example loaded back in a browser all behave as expected; axe clean at 1100 px light and 390 px light and dark; no sideways scroll.
