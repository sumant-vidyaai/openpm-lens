# Decisions and roadmap

Decisions agreed with the project owner on 15 October 2026.

## Decisions

| Topic | Decision |
|---|---|
| Licence | Apache-2.0 (explicit patent grant, clear contributor terms). |
| Hosting | Cloudflare Pages free plan (static files; no project data ever reaches the host). Indian mirror optional later. |
| Blocked browsers | Tools that block direct browser calls (e.g. Jira Cloud) are file-import only in v1. No hosted proxy, because it would break "no data to any server". |
| Live API connectors | Only where the tool allows browser calls (e.g. Azure DevOps). Optional and clearly marked; tokens in memory only. |
| Metric grouping | Two neutral tags per card: `domain` (broad group) and `area` (traditional group). No third-party framework names or trademarks. |
| Sample data | Synthetic only, imitating each tool's export format. From the owner's PPM exports, column headers only, never rows. |
| Missing planned hours | Default "exclude and flag". Optional "treat as zero" with the assumption flagged. Missing actual hours or percent complete always exclude. |
| Percent complete | Visible per-tool setting (tool-reported, 0/100, 50/50, status-based). |
| Stack | TypeScript, Vite, React, Vitest; static site on Cloudflare Pages; offline support via service worker; GitHub Actions for tests. |
| Privacy rules | No tracking or analytics; nothing loaded from other websites at runtime; strict browser security policy; downloadable release bundle with checksum; dependency list kept small. |

## Connector order (proposed)

1. Generic CSV/XLSX importer with column mapping.
2. MS Project XML (MSPDI).
3. Jira CSV.
4. Azure DevOps (CSV, then browser REST).
5. Flow-focused tools (Linear, GitHub Projects, Trello, ClickUp).
6. Enterprise PPM (Clarity, Workfront, ServiceNow, Planview, Smartsheet).

## v0.12 – More metrics (Batch 3)
**Forecast (Import tab):** EAC, ETC, VAC and TCPI. The user chooses how the rest of the work is expected to go (three EAC methods: BAC/CPI; AC + BAC - EV; AC + (BAC - EV)/(CPI x SPI)); the choice is shown. BAC = planned hours of the tasks used, not necessarily the whole project (stated on screen). TCPI is withheld with a reason when spend already equals or exceeds the budget (or forecast). The CPI x SPI method needs a status date. Included in the summary CSV.
**Earned schedule (Import tab):** ES = C + (EV - PV_C)/(PV_C+1 - PV_C); SV(t) = ES - AT; SPI(t) = ES/AT. Formulas checked against Walt Lipke's introduction at earnedschedule.com (the source gives no rule for after the planned end). Our rules, stated on screen: AT counts counted days (weekdays or calendar days) from the first planned start to the status date, both included, and keeps counting after the planned end; if all planned work is earned, ES is capped at the planned duration. The curve uses only tasks usable for schedule measures; a test checks the curve matches PV at the status date. Verified against an independent Python calculation (ES 8.7143, AT 13, SPI(t) 0.6703 for the Website redesign sample).
**Flow metrics (new tab):** WIP, throughput, cycle time, work item age. Definitions follow the Kanban Guide (prokanban.org): WIP = started not finished; throughput = finished per unit time; cycle time = started to finished; age = started to now. The guide does not say how to count days or which percentile method, so our rules (on screen): calendar days counted inclusively (same day = 1); nearest-rank percentiles, shown only with at least 5 finished items else "Insufficient data"; window = last N blocks of 7 days ending on the status date (not calendar weeks). Status date is required, never assumed. "Created" is never guessed as a start date (it would be lead time; warned if chosen). Left out and listed: cancelled, unclear dates, marked done without a done date, done before start, no dates, starts after status date. Finished items without a start count in throughput only. Every item is accounted for exactly once (test).
- Tests: 190 pass. Open: flow metrics need real header lines from Jira/Azure DevOps/etc. to suggest start/done columns; Jira's standard CSV has no "work started" date (needs changelog), so users must supply one.

## v0.13 – Batch 3b part 1: Schedule, Cost in money, Resources (inserted before Batch 4, agreed with the user)
**Why:** the app covered cost and schedule in hours and flow, but not resource, quality or cost in money. Plan agreed: Batch 3b before Batch 4, in two deliveries (v0.13: schedule extras, money, resources; v0.14: quality, charts, MS Project XML).
**Architecture:** the Import tab now publishes its worked-out data (table, items, hours tasks, schedule tasks, status date, date order, day count) to the other tabs (`SharedData`); rows line up one-to-one. New tabs reuse the Import tab's column and unit choices and add only their own picks. All tabs stay mounted (hidden) so loaded files and settings survive tab changes (previously the Import tab lost its file when you left it).
**Schedule tab:** variance = actual finish - planned finish in calendar days (positive late); on time = on or before planned finish; overdue = open task whose planned finish is before the status date. On-time % and median need at least 5 finished tasks (else "Insufficient data"). Left out and listed: cancelled, unclear dates, no planned finish, marked done without a finish date. Every task is counted exactly once (test).
**Cost in money tab:** hours x hourly rates entered by the user (default rate and/or per person); one currency, label only, no conversion or lookup; invalid rates ignored; a task without any applicable rate is left out and listed (never a guessed rate). Same task rules as hours. A task naming several people (";" separated; commas are read as part of one name) uses the default rate only if none of them has an own rate, else it is left out. Money CPI can differ from hours CPI (stated). Forecast in money offers the two methods that need no planned value.
**Resources tab:** planned hours spread evenly over planned weekdays (or calendar days, from the Import setting), summed per person per week (weeks start Monday); utilisation = load / weekly capacity (default 40 h, editable, own capacity per person); weeks above a user-set limit (default 100%) are flagged with a symbol. Tasks naming several people are left out (split unknown); unassigned work has its own row. Planned vs actual per person uses tasks that have both. Capped at 104 weeks shown. Rules are this app's own arithmetic, not a standard.
**Verified:** all three checked against independent Python calculations on a made-up team file (60% on time, EV 6,240, AC 6,530, BAC 9,300, weekly utilisation per person). 207 tests pass.
**Open / known limits:** CSV exports from MS Project may include summary (parent) rows whose hours repeat their children's, which would double count; to be handled with the MS Project XML importer (which flags summary tasks) in v0.14. Assignee, type and severity columns are not yet in the Tool coverage matrix.

## v0.14 – Batch 3b part 2: Quality, charts, MS Project XML
**MS Project XML (MSPDI):** read in the browser with `fast-xml-parser`; files with a DOCTYPE/ENTITY are refused (entity-expansion defence), 25 MB cap. Element names and formats (Work/ActualWork as PT…H…M…S, ISO dates, PercentComplete, PercentWorkComplete, Baseline) checked against Microsoft's documentation. Left out and counted: summary tasks (their work repeats their sub-tasks'), tasks with no name. Plan comes from baseline number 0 (else the only baseline present, else the current schedule with a visible warning). Progress uses % work complete when any task has it, else % complete. Durations or dates in unexpected form are blanked and counted, never guessed. Several assignees are joined with "; ". Table headers are chosen so no other tool adapter mistakes the file for its own.
**Assumption still open:** Microsoft's reference does not say what a baseline "Number" means; Number 0 is assumed (Project's usual main baseline) and this is shown on screen. Needs a real MS Project XML file to confirm.
**Quality tab (defects):** the user picks the type, severity, created, resolved and optional "found in" columns and ticks which type values are defects (ticks pre-set from names like bug/defect/incident, editable). Measures: counts open/closed, defect share, open age (mean, median, oldest), resolution time (mean, median, 85th percentile), severity table, open list oldest first, removal efficiency = found before release / all defects x 100, only when the user ticks which "found in" values mean after release (nothing ticked for them). These measures have no single standard, so the rules are this app's own and said on screen; percentages and percentiles need at least 5 items. Defect density is not offered (needs code size). Days inclusive. Left-out items listed.
**Charts:** plain SVG, no inline styles (CSP). Earned-value chart (planned value line, earned value at status date), throughput columns, cycle-time scatter with 50th/85th percentile lines. Palette, mark sizes, gridlines and light/dark pattern follow the dataviz guidance; each chart has a legend where there are two series, labels on key points, hover text, a "Show as table" view, and a text description for screen readers. The actual-cost point was left out of the curve for now.
**Verified (browser vs hand calculation):** MSPDI sample PV 60.57, EV 52, SPI 0.86, SV -8.57; defects: 7 defects, 3 open ages 11/10/8, mean resolution 4.25 (shown 4.3), removal efficiency 5/7 = 71%. No console errors; no horizontal scroll at 380 px. Tests 231 pass; typecheck and build pass; npm audit 0 vulnerabilities.

## v0.18 – Fill-in template (roadmap batch A)
**Why:** the user's idea: define our own template that people fill in and upload to get the numbers. It also removes the need to name which project tool someone uses.
**What was built:** a downloadable **Excel workbook** (sheets: Start here, Tasks, Settings, Rates) and a **plain CSV** with the same 18 column headings (Project, Programme, Team, ID, Task, Type, Status, Assignee, Planned start, Planned finish, Actual start, Actual finish, Estimate (h), Actual (h), % complete, Created, Severity, Found in), plus a **filled made-up example** of each (two projects, 14 tasks). They are generated by `scripts/make_template.py` and live in `packages/web/public/templates/`. A test checks the CSV headings equal `TEMPLATE_COLUMNS` in the code.
**Rules of the template (shown to the user):** effort in hours, percent 0 to 100 (write 40, not 40%, because Excel stores 40% as 0.4), dates as year-month-day typed as text so Excel cannot reinterpret them (real date cells are also read), a blank is "not known" and never 0. Dropdowns for Type, Status, Severity, Days counted, Progress rule; validation for dates, hours (0 or more) and percent (0 to 100).
**Settings sheet:** status date (blank by default, never assumed), hours per working day (8), weekdays or all days, weekly capacity (40), currency label, default hourly rate, green from (0.95), amber from (0.85), progress rule, in-progress credit. Invalid values are ignored and listed on screen, never guessed; amber must be below green. **Rates sheet:** person and hourly rate; bad rows listed.
**Recognition:** a file is "our template" only if it has Task, Status, Estimate (h), Actual (h), % complete, Planned start and Actual start (so an ordinary file with similar names is not claimed). Import then sets the mapping, hours, 0-100 percent, progress rule, status date, hours per day and day counting from the file; the Cost tab gets currency, default rate and person rates; Resources gets the capacity; Overview uses the template's green/amber limits (and says so); Flow gets the status date; Portfolio splits one file into **one project per value of the Project column** (Programme and Team taken from the rows; a conflict is reported) and takes the settings too. A CSV has no Settings sheet, so the status date is chosen on screen.
**Readiness check:** on Import and Overview, per area, "N of M tasks have what is needed" (cost, schedule, flow, resources, quality) with what is missing. Cancelled tasks are not counted and the count is shown.
**Bugs found and fixed while testing:**
1. A **cancelled task with a % complete was counted** in budget and earned value under the "use the % in my file" rule (the cancelled exclusion only applied to the other rules). Now a cancelled task is excluded under every rule (new tests). This changes results for any file that has cancelled tasks with a % under that rule.
2. "Actual finish" was not recognised as a finish date by the Flow/Quality/Schedule guessers (it would have picked "Resolved"). Now matched first.
3. **Excel sheets larger than about 512 KB once unpacked could not be read** under the app's security policy: the library unpacks big sheets in a web worker, which the policy blocks. Small workbooks were checked and worked before this change. The app now uses the library's main-thread build and, if a workbook still cannot be read, says so in plain words and suggests saving the sheet as CSV. The template pre-formats 500 rows (not 1000) to stay under the limit; dropdowns and checks still cover 2,000 rows.

## v0.19 – Batch 1: Explain and accuracy
**Why:** after v0.18 the numbers were there but not the "why" or the timing. Agreed roadmap Batch 1 (docs/roadmap.md).
**What was built:**
1. **Holidays and leave.** Template sheets **Holidays** and **Leave** (and a holiday box on Portfolio). Holidays apply only when days are counted as weekdays; they are skipped in planned value, earned schedule and the planned-value curve. Leave: each Monday-to-Friday day a person is away (or a holiday) takes one fifth off that person's weekly capacity. A week with no capacity but planned work counts as over the limit (utilisation shown as "no capacity"). Resources shows "(capacity N h)".
2. **Why is it red? and Fix these first (Overview).** Tasks ranked by how much they pull cost (EV minus AC) or schedule (EV minus PV) below plan, each with its share of the shortfall; tasks that are ahead are listed separately. "Fix these first" groups tasks left out of a measure by reason (for example no actual hours), cancelled tasks skipped.
3. **Milestones (Schedule tab).** Type = Milestone. States: done on time, done late, done with no date, overdue, due soon (14 days or less), upcoming, no planned date. Calendar days. No forecast yet (Batch 4).
4. **Actual-cost line** (dashed) on the earned-value chart. **Assumption, shown on screen:** each task's actual hours are spread evenly over its counted days, from actual start to actual finish or the status date; task lists do not record spending by day. The chart says how many actual hours it covers.
5. **Monthly cash flow (Cost tab).** Planned vs actual cost by month, same even-spread assumption; a span with no counted day goes on its end date; undated tasks are listed.
6. Scrollable table areas are now keyboard-focusable (axe finding on narrow screens).
**Verified:** independent Python calculations matched the app (cost, planned value with a holiday, money, cash flow, flow, quality, schedule, resources). axe-core: 0 violations, 0 px overflow, light and dark, 1100 and 360 px. Example workbook regenerated with a holiday (2026-03-25) and leave (Kiran, 2026-03-30 to 04-03).
**Limits:** milestone forecast deferred to Batch 4; a person's "peak week" ignores a no-capacity week; the actual-cost spread is an assumption; at the status date the EV and AC chart labels can sit close together; Excel features not tested in Microsoft Excel itself.

## v0.20 – Batch 2: Risks, issues and changes
**Why:** roadmap Batch 2. A project status is incomplete without what could go wrong, what has gone wrong and what has been added to the plan.
**What was built:** three optional template sheets, **Risks**, **Issues** and **Changes** (read by heading, so re-ordered columns still work), a new tab **Risks, issues, changes**, and a summary panel on Overview. A CSV or a non-template file has no such sheets, and the tab says so.
**Formula (checked against two independent sources):** risk score = probability x impact, each a whole number 1 to 5, giving 1 to 25. One source gave bands Low 1-6, Medium 7-12, High 13-25; the other gave only colours. Sources differ on the band limits, so these are **starting values (Medium from 7, High from 13), changeable on the Settings sheet**, and labelled "not a standard". Scores are never added together (they are an ordering, not a quantity). No money value (expected monetary value) is built; it would need judgement inputs.
**Rules:** a blank or unreadable value is "not known", listed with its row, never 0 and never guessed (a risk with no probability or impact is "not scored"; a status that is not one of the list is "not known"). Heat map counts open scored risks only. Overdue risk action = open risk, action due before the status date, no "Action done" date. Issue age = status date minus Raised, calendar days; resolved issues show Raised to Resolved. Changes: only Approved ones are added, in Decided-date order, with running totals; an approved change with no stated cost or days is counted as "not stated" and reported, not as 0. **Scope growth = approved cost hours / "Original budget (h)"** (a new Settings value the user enters; without it, scope growth is not shown and the screen says why). Days waiting = status date minus Requested for undecided requests.
**New settings:** Original budget (h), Risk medium from (7), Risk high from (13). Invalid values are ignored with a message; medium must be below high.
**Verified:** hand-worked tests (23 new, 293 in all). In the browser with the example workbook (checked independently by hand): 4 open risks (1 high, 2 medium, 1 low), R-1 action 11 days overdue, 1 open risk with no owner; 3 open issues, oldest 30 days, 1 past due by 11 days, resolved issues average 3 days; 3 approved changes +38 h and +5 days (running +14, +54, +38 h), scope growth 38/540 = 7.0%, 1 request waiting 16 days. Same in Asia/Calcutta and America/Los_Angeles. axe-core: 0 violations on Overview, the new tab and Learn in light and dark at 1100 and 360 px; 0 px overflow (a hidden-text overflow in the heat map was found and fixed). Heat-map cells carry the count, a symbol and a letter as well as colour.
**Limits:** one risk/issue/change list per file (the Project column is not used yet; Portfolio roll-up is Batch 9); no risk trend over time (Batch 3 snapshots); no cost-in-money for risks; the Risk and Change task types still exist in the Tasks sheet for old files but the new sheets are the place for them; Excel features (dropdowns, validation) not tested in Microsoft Excel itself.

## v0.21 – Batch 3: Snapshots and trends
**Why:** a single status says where the project is, not whether it is getting better or worse. Roadmap Batch 3.
**What was built:** a new tab **Snapshots and trends**. A snapshot is a dated copy of the headline numbers: earned value, actual cost, budget, planned value, schedule earned value, task counts by status (not started, in progress, done, cancelled), open defects, and (if the file has the Risks, Issues, Changes sheets) open risks by band, open issues and approved change hours and days. It holds **totals only, never task names or people**; this was checked on a real snapshot file (no task, person or risk text in it).
**How snapshots are kept:** in the browser's own storage on this device (never uploaded). If storage is blocked (a private window), snapshots are kept until the tab closes and a warning says so. Every snapshot can be downloaded as a JSON file, all of them as one file, and files can be added back, so a copy can be kept elsewhere or shared. A file read back is **never trusted**: format, version, label, a real calendar date, finite numbers and whole non-negative counts are checked, unknown fields are dropped and a bad file is refused with the reason (a bad date, text where a number belongs, not a snapshot file). Files over 2 MB are refused.
**Rules:** a snapshot is filed under its label (default: the file name, editable) and its **status date**; saving the same label and status date again replaces the earlier one (stated on screen) so a double save does not double count. Trends are ordered by status date, not by when it was saved. Each label has at most one **baseline** (a choice the user makes, not decided by the app). CPI and SPI are worked out when read (earned value / actual cost; schedule earned value / planned value) and are null, never 0, when a part is missing or the divisor is 0. A number not known when the snapshot was taken stays "not available" and is never treated as 0.
**Views:** compare any two snapshots (default: baseline against latest) with the change, the days apart and the budget change in hours and percent; CPI and SPI over time with the 1.0 line; **burnup** (scope = planned hours, work done = earned value); **burndown** (scope minus earned value); **cumulative flow** (stacked counts of done, in progress, not started; cancelled left out); **throughput between snapshots** (tasks that became done since the previous snapshot / weeks between the two status dates; none if the done count fell or the dates are the same); open defects; open risks, high risks and open issues. The horizontal position is proportional to the days between status dates. Every chart has a legend, hover details and a "Show as table" view; notes under each chart state what it can and cannot say. Count charts use whole-number ticks.
**Definitions that may surprise:** open defects = rows whose Type contains bug, defect, incident or problem and that are not done or cancelled (same words as the Quality tab's default; needs a Type column). Throughput here is a rough rate from two dates; the Flow tab, which uses actual finish dates, is the precise one. "Days since last update" is counted from the latest snapshot's status date to today's date on the device.
**Verified:** 21 new tests with hand-worked numbers (293 became 314 in all): CPI 200/250 = 0.8 and 310/385 = 0.8052, SPI 180/300 = 0.6 and 310/374 = 0.8289, remaining 400 and 284, throughput 3 tasks in 14 days = 1.5 per week, compare budget -6 h and earned value +110 h, one baseline per label, replace on same label and date, ten kinds of bad file refused. In the browser with the example workbook, snapshots at four status dates matched a separate Python calculation: planned value 108, 207.3 (no holiday) or 209.7 (with the 25 March holiday), 311.5 and 370.33 hours; SPI 2.87, 1.48, 0.995 and 0.837; cost earned value 326, actual cost 385, CPI 0.8468; 13 tasks not cancelled; 1 open defect. Snapshots survived a page reload, a download then delete-all then re-upload restored all four, and a bad file and a non-JSON file were refused with messages. axe-core: 0 violations and 0 px overflow, light and dark, 1100 and 360 px; no console errors; same results in two time zones.
**Limits:** the trend lines only have as many points as snapshots saved, so they are empty until the project is saved at least twice; the example workbook cannot show change over time on its own (the same data was saved at four dates, so only planned value and SPI move); snapshots are per browser and per device, so sharing means sending the file; no automatic reminder to save (the app does not run when closed); one baseline per label, with no re-baseline history yet; risk and issue trends use only open counts.

## v0.21.2 – Report with charts as PDF (user request)
**Request (user):** the snapshot trends should be downloadable as PDF or Excel so a person can see the charts; a CSV shows only plain data.
**Options weighed:** (1) PDF through the browser's print window; (2) a single HTML file; (3) an Excel file with real charts; (4) CSV only. Excel with real charts cannot be produced in the browser without a heavy extra library, and it would carry pictures rather than editable charts, so it was not built. A hand-made Excel file with three charts was provided once as an example from the user's own two snapshots.
**What was built:** a button **Download report (PDF, with charts)** on Snapshots and trends. It opens the browser's print window; the person chooses "Save as PDF". The page title is set to "openpm-lens report - <label> - <latest status date>" while printing so the suggested file name is meaningful, then restored. The printed report has a header (label, date prepared, number of snapshots, status date range, baseline, latest CPI and SPI, a note that limits are starting values and data stayed on the device), the comparison table and all charts, with the controls hidden; the "Show as table" disclosures are hidden in print. The browser cannot save a PDF silently without a library, so the print window is one extra click; this is stated on screen.
**Bug found and fixed (older, found by this work):** printing while the screen was in dark mode produced a dark page with chart titles in white on white. The earlier print rule lost to the dark theme. Printing now always forces a white page and dark text (CSS variables set with !important for all three theme selectors), so every tab prints correctly from dark mode as well.
**Verified:** a real PDF generated from the page in dark mode (4 snapshots, 5 A4 pages): white page, readable titles, table and all charts present; the page title was set at print and restored after; no console errors; axe-core clean on the tab.
**Limits:** the PDF is made by the browser, so the layout varies slightly between browsers; the charts print as vector pictures (not editable); the one-page status report with commentary and forecast comes in Batch 4.
